The problem

Nobody has an afternoon.

A dependency advisory lands. Someone has to work out whether this repository is genuinely affected, whether the fix is a one-line bump or a breaking change, whether the test suite survives it, and then write the pull request. That is an afternoon per advisory, and most teams do it late — or not at all.

Every software team on earth has this backlog. So the work is not knowledge work any more; it is repetition at scale, and repetition is exactly what an agent should be doing.

The bottleneck is not knowledge. It is that nobody has an afternoon.

So SENTINEL does the afternoon. It stops at the one step that is irreversible.

What it does

Eight stages. The last one is yours.

Everything up to the pull request is autonomous. The pull request itself is not — that is the irreversible step, and the agent stops there and asks.

  1. STAGE 01

    Inventory

    Reads package.json and the lockfile from GitHub, resolving real installed versions rather than declared ranges.

  2. STAGE 02

    Triage

    Queries the GitHub Advisory Database (OSV fallback) and keeps only advisories whose version range actually matches.

  3. STAGE 03

    Delegate

    Spawns one subagent per affected package, each with a clean context window — ten CVEs do not share one context.

  4. STAGE 04

    Assess

    Works out whether each upgrade is a patch, minor or major bump, and how widely the package is imported.

  5. STAGE 05

    Plan

    Collapses findings into one safe target version per package — the highest fix version, so no advisory is left open.

  6. STAGE 06

    Patch

    Generates the updated package.json, preserving the project's existing range operators.

  7. STAGE 07

    Verify

    Installs and runs the test suite in an isolated Daytona sandbox.

  8. STAGE 08 · GATE

    Propose

    Opens the pull request. Pauses. Waits for a human. The turn ends and nothing happens until a person clicks.

The 7 MCP tools

Safety is declared on the tool, once.

TrueForge resolves its @read-only / @destructive approval selectors from these annotations, so the policy lives next to the implementation and both front ends inherit it automatically.

Tool Annotation Approval What it does
scan_dependencies readOnlyHint no Reads package.json + lockfile, resolving installed versions.
lookup_advisories readOnlyHint no GitHub Advisory Database with OSV fallback; range-matched only.
assess_blast_radius readOnlyHint no Bump classification plus how widely the package is imported.
summarise_triage readOnlyHint no One safe target version per package. No network access.
propose_patch readOnlyHint no Returns updated file content. Writes nothing to GitHub.
open_pull_request destructiveHint yes Branch + commit + PR. Irreversible, so it is gated.
merge_pull_request destructiveHint yes Changes what ships. Gated behind a human click.
Control & safety

Structural, not a prompt the model can talk its way out of.

Defence in depth on the irreversible path

  • ✓The agent spec gates @destructive and names both tools literally.
  • ✓Destructive handlers check the kill switch before any network call.
  • ✓GitHubClient re-checks it again at the point of mutation.
  • ✓Branch names are generated by us and validated against git's ref rules.
  • ✓The web API only accepts approvals the harness actually raised.

Failing safe, and keeping secrets out

  • ✓Empty input, EOF and Escape all deny. Denial is the default.
  • ✓Keys live only in .env, git-ignored, read in exactly one place.
  • ✓The browser never talks to the harness or a provider directly.
  • ✓Two-layer redaction scrubs every log line, tool result and SSE frame.
  • ✓The MCP token is compared in constant time.
Installation

Three commands. Pick the path that fits.

All downloads come straight from GitHub — there is no registry, no mirror, and nothing to sign up for.

The packaged CLI from the v0.2.0 release. Requires Node.js ≥ 22.14.

  1. 1 Download the package
    curl -L -O https://github.com/geohot0199/sentinental/raw/refs/tags/v0.2.0/releases/sentinel-strike-team-v0.2.0.tgz
  2. 2 Verify (optional)
    sha256sum sentinel-strike-team-v0.2.0.tgz

    b14628e81bbcd73dc46429bb238b04a71c5524420a618a6757d4c89d9f5cef5c

  3. 3 Install globally
    npm install --global sentinel-strike-team-v0.2.0.tgz
  4. 4 Add your keys, then run
    cp .env.example .env && sentinel

Full source, with the web console and the MCP tool server. Needs the TrueForge harness running alongside it.

  1. 1 Start the TrueForge harness
    npx @truefoundry/trueforge@latest

    Keep it running in a separate terminal.

  2. 2 Clone and install
    git clone https://github.com/geohot0199/sentinental.git && cd sentinental && npm install
  3. 3 Configure
    cp .env.example .env
  4. 4 Run it
    npm run web

    Web console at http://localhost:3000. Or npm run cli for the terminal client, npm run mcp for just the tool server.

A scripted model endpoint is included, so you can see the whole path — real advisory data, real tools, real approval gate — without spending anything.

  1. 1 Start the scripted model
    node --experimental-strip-types scripts/mock-model.ts &
  2. 2 Point SENTINEL at it
    echo "SENTINEL_DEMO_MODEL_URL=http://127.0.0.1:8899/v1" >> .env
  3. 3 Run the console
    npm run web

Before you start

  • ✓Node.js ≥ 22.14 — the CLI uses type stripping
  • ✓One model key — OpenAI, Anthropic or Gemini
  • ✓GitHub token — fine-grained PAT, Contents + PRs read/write
  • !Daytona key — recommended; without it every patch is unverified

Scope your token properly

Grant the GitHub token access only to the repositories you want SENTINEL to touch. The only writes are the branch and the pull request, and both are gated behind you.

Running a demo? Set SENTINEL_ALLOW_REMOTE_WRITES=false and destructive tools refuse before any network call.
