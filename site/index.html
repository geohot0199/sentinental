THE PROBLEM

Nobody has an afternoon.

A dependency advisory lands. Someone has to figure out if this repo is actually affected, if the fix is a one-liner or a breaking change, if tests survive it, and then write the PR.

That's an afternoon per advisory. Most teams do it late or not at all. Every software team on earth has this backlog.

"The bottleneck is not knowledge. It is that nobody has an afternoon."

So SENTINEL does the afternoon. It stops at the one step that is irreversible.

WHAT IT DOES

Eight stages. The last one is yours.

Everything up to the pull request is autonomous. The PR itself is not — that's the irreversible step.

01

Inventory

Reads package.json and the lockfile from GitHub. Resolves real installed versions, not declared ranges.

AGENT
02

Triage

Queries GitHub Advisory Database (OSV fallback). Keeps only advisories whose version range actually matches.

AGENT
03

Delegate

One subagent per affected package. Clean context window each. Ten CVEs don't share one context.

AGENT
04

Assess

Works out if each upgrade is patch, minor, or major. Checks how widely the package is imported.

AGENT
05

Plan

One safe target version per package — the highest fix version. No advisory left open.

AGENT
06

Patch

Generates updated package.json. Preserves the project's existing range operators.

AGENT
07

Verify

Installs and runs the test suite in an isolated sandbox.

AGENT
08

Propose

Opens the pull request. Pauses. Waits for a human.

YOU
The last row is the point. The pause is real: the turn ends, the console shows the full tool call, and nothing happens until you click.

CONTROL & SAFETY

Structural, not a prompt.

Safety the model can't talk its way out of.

1

Declared approval policy

MCP tool annotations define readOnlyHint and destructiveHint. Classification lives next to implementation.

ToolsGate
scan_dependencies, lookup_advisories, assess_blast_radius, summarise_triage, propose_patchnone
open_pull_request, merge_pull_requestyes
2

Defense in depth

  • Agent spec gates @destructive and names both tools
  • Kill switch checked before any network call
  • GitHubClient re-checks at point of mutation
  • Branch names generated — model never supplies a ref
  • Web API only accepts approvals for real tool calls
3

Fails safe

Empty input, EOF, Escape, unparseable — all deny. Deny button holds focus in the web UI.

4

No secrets, ever

  • Keys in .env only, git-ignored, read once
  • Browser never talks to harness or provider directly
  • Two-layer redaction on every log, tool result, SSE frame
  • npm run scan:secrets fails CI on credential shapes

QUESTIONS

Straight answers.

Will it open a PR without asking?

No. open_pull_request and merge_pull_request are destructiveHint. The harness raises a real gate. The turn ends and waits.

Do I need an API key to try it?

No. A scripted model ships with the repo. See the No-Key Demo tab.

Which ecosystems?

Node/npm. Reads package.json + lockfile, triages against GitHub Advisory Database with OSV fallback.

What without a sandbox key?

Every patch is reported as unverified. It never guesses a fix works.

Can I run read-only?

Yes. SENTINEL_ALLOW_REMOTE_WRITES=false. Destructive tools refuse before any network call.
